# Draft: RoBoard 多智能体指挥舱 MVP 设计

## 目标（用户原话/意图）
- 方向：把“配置、查看日志、查看状态”等工程师动作，尽量用游戏化元素承载（角色、心情/状态、关卡、掉落、收集）。
- 技术简化：用 Web 的 3D 画面暂代 Godot；后端用 FastAPI；聚焦 Playwright（/ Playwright MCP）作为简化“沙箱/执行器”。
- 需求：调研类似竞品/相邻产品，并给出一份能突出亮点的“完整MVP设计”。
- 商业目标：订阅 + 皮肤等内购组合，目标价位/ARPA 约 $50+（表述为“订阅+皮肤”，需进一步确认具体档位与口径）。

## 交流与记录偏好
- 语言：尽可能使用中文交流与记录（已确认）。

## 已确认的关键选择（来自你的回答）
- 目标用户：内容创作者
- 首发商业化：先不接真实支付（MVP做价格墙 + 兑换码/手动开通）
- 执行形态：自建单机（Docker/Compose 跑 Playwright/Playwright MCP）
- 结果交付优先：邮箱/Telegram

## 第二轮澄清（来自你的回答）
- 任务模板取向：不希望由我们预先限定“主打哪3个模板”，更倾向把“业务/任务创建”交给用户决定（意味着MVP需要提供某种“用户自定义任务创建”能力，而不仅是固定模板库）。
- LLM 总结：默认开启（作为核心卖点之一）。
- 登录型任务：认为这是 Playwright 服务能力，不希望现在把它当成主要决策点（但架构仍需预留凭据/回放脱敏/人工介入）。
- 运行方式：手动触发 + 定时任务都要。
- 3D 风格：极简但高级。

  - 网关单独服务

## 已有设想（从粘贴内容提炼）
- 三层结构：
  - Agent层：等级/技能树（访问速度、容错、并发数），心情/状态（超载罢工→需要“安抚”=暂停任务）。
  - 任务层：现实任务抽象为“关卡”（难度星级、预计时长、推荐Agent、掉落金币/道具）。
  - 成长&收集层：成就、皮肤、工作台场景（办公室装修）。
- MVP架构倾向：端云分离，但早期避免过度架构；WebSocket 即时回执；“预估完成时间 + 实际结果”两段式反馈。
- 运维倾向：MVP不做K8s，Compose/脚本拉起即可。

## 调研要点摘录（已完成，待在计划中落地）

### 竞品/相邻产品（结论性整理）
- 大类 1：AI Agent / AI IDE（Devin、Cursor、Replit Agent 等）
  - 特点：强调“能做事/能写代码”，定价常见 $20/mo（个人）到 $60/mo（高用量）乃至 $200/mo（极高用量）；但普遍缺少“任务执行可回放资产化”的产品层表达。
- 大类 2：工作流自动化（Zapier、Make、n8n）
  - 特点：模板与集成多，但交互形态偏工程/表单；用户常抱怨复杂度与成本随用量增长。
- 大类 3：浏览器自动化基础设施（Browserbase、Browserless 等）
  - 特点：把“并发浏览器/会话录制/代理/隐身/验证码”做成基础设施；但缺少面向非工程用户的“控制层体验”。

### 差异化机会（与你的方向强相关）
- 3D 不是为了“酷”，而是承担“并发/状态/瓶颈/失败点”的空间化表达：代理在房间里接单、执行、产出、疲劳，形成一眼可理解的系统。
- 把“任务=关卡”做成可复用资产：每次执行生成事件时间线 + 关键帧截图 + 结构化产物（JSON/CSV/Markdown），失败可定位到具体关卡步骤。
- 人机协作要有明确的“介入点”：遇到登录/验证码/二次确认时，进入 requires_input 事件，前端给出提示并暂停。

### Playwright / Playwright MCP 关键点
- Playwright MCP：官方定位为 MCP server，为 LLM 提供浏览器自动化能力（基于可访问性快照等结构化信息）。官方也提醒：对“高吞吐 coding agent”，CLI+Skills 可能更省 token（对我们产品侧影响不大，但意味着协议设计要克制）。
- 自建单机可行，但要把 API 与执行 worker 隔离（不要在 FastAPI 主进程直接跑 Playwright），并强制并发配额。
- 已知高风险：CAPTCHA、登录/2FA、反爬/风控、速率限制。MVP 应优先选择“公共页面/低风控路径”的任务模板；必要时提供人工介入。

### 变现（先不接支付也要设计“价值锚点”）
- 公平原则：皮肤/装饰应不影响任务成功率（避免 pay-to-win 观感），核心价值收费点应是并发、回放保留、计划任务、模板参数集保存、失败重试等“效率与资产化”。
- $50+ 的可信锚点：对内容创作者，能证明节省时间（日报/周报自动产出）+ 结果可复用（模板/报表/可回放）+ 通知与交付（Telegram/Email），比“按任务次数计费”更不焦虑。

### Oracle 建议（对MVP范围的约束）
- Wow-factor 的闭环：下单任务→3D 代理“在跑”→拿到可复用产物→XP/掉落。
- 不做：多人3D同屏、在线脚本编辑器、分布式调度/多区域、多代理自由协商推理。
- 强制：WebSocket 事件流协议版本化；Secrets/回放脱敏从第一天开始。
