# Linpo v0.1 Observer Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 将 Linpo v0.1 的 observer 方向从产品/架构共识推进到第一阶段可执行实现计划，先交付“agents 列表页 + 单 agent 拓扑详情页”的最小闭环。

**Architecture:** 先冻结文档与最小数据契约，再推进页面骨架、节点展示与事件面板。Linpo 在此阶段保持 observer 角色，不引入控制面、复杂编排与资源监控。

**Tech Stack:** 当前仓库既有前后端代码、文档目录、FastAPI / frontend 工程痕迹；具体实现细节在执行任务时以现有代码为准，不新增与 v0.1 无关的大型基础设施。

## 2. 第一阶段交付目标

第一阶段只追求一个最小闭环：

1. 用户能进入 agents 列表页
2. 用户能看到最小 agent 列表字段
3. 用户能进入单个 agent 详情页
4. 用户能看到完整 agent / subagent 拓扑图
5. 用户点击节点后能看到最小详情面板
6. 系统能展示最小历史事件记录

如果这个闭环不能稳定成立，就不应继续扩张任务视图、决策视图、资源视图或控制能力。

---

## 3. 实施原则

- 先补齐文档，再改代码
- 先做静态结构可见性，再做动态细节
- 先做最小契约，再做扩展语义
- 先保证 observer 边界清晰，再考虑后续演进
- 保持 YAGNI，不预建控制面和平台大骨架

---

## 4. 阶段拆解

### 阶段 A：文档与现状校准

**目标**：让实现拥有稳定约束来源。

**交付物**：
- PRD 文档
- 架构文档
- 实施计划文档
- README 文档索引更新

**完成标准**：
- `docs/prd/`、`docs/architecture/`、`docs/plans/` 对 observer 方向表述一致
- README 可作为当前文档导航入口

---

### 阶段 B：代码现状盘点与实现入口识别

**目标**：明确当前仓库哪些代码可复用，哪些仍停留在 v0.0 语义。

**建议动作**：
- 盘点前端入口、页面结构、现有组件
- 盘点后端 API、领域模型、fixtures、测试目录
- 标记与辩论 demo 强绑定的模型/接口
- 识别可最小复用的数据流和页面骨架

**完成标准**：
- 得到一份“保留 / 替换 / 暂不使用”的代码现状清单
- 能明确 observer v0.1 第一版落地对应的文件集合

---

### 阶段 C：冻结最小数据契约

**目标**：把产品与架构中的字段定义落成可实现契约。

**需要冻结的核心对象**：
- Agent 列表项
- Agent 详情拓扑节点
- 节点详情面板数据
- 历史事件记录项

**最小字段建议**：
- 列表项：名称、状态、是否活跃、最近活跃时间
- 节点：名称、状态、是否活跃、子节点数、父子关系
- 节点详情：最近开始活跃时间、当前是否活跃、历史事件记录
- 事件：时间、类型、可读描述

**完成标准**：
- 前后端对最小数据结构有一致定义
- 未提前冻结 v0.2+ 字段

---

### 阶段 D：实现 agents 列表页最小闭环

**目标**：交付纯列表首页。

**页面要求**：
- 一行一个 agent
- 展示名称、状态、是否活跃、最近活跃时间
- 支持进入 agent 详情页

**完成标准**：
- 列表页可稳定渲染最小字段
- 不引入卡片网格、复杂筛选、大盘式仪表盘

---

### 阶段 E：实现 agent 详情页拓扑视图

**目标**：交付完整拓扑默认展示。

**页面要求**：
- 显示根 agent 与 subagents 的关系
- 默认展示完整结构
- 节点展示最小字段
- 不做智能聚焦、高亮路径、复杂解释层

**完成标准**：
- 用户能稳定区分根节点与子节点
- 用户能从图上识别基础状态与结构关系

---

### 阶段 F：实现节点详情面板与事件记录

**目标**：交付“结构优先，细节后置”的状态查看能力。

**面板要求**：
- 最近开始活跃时间点
- 当前是否活跃
- 历史事件记录

**事件要求**：
- 至少支持结构 / 状态事件与最小任务边界事件
- 记录格式先服务于可读性，而不是复杂分析

**完成标准**：
- 用户点击节点后能理解其近期状态变化
- 不引入控制按钮、资源面板、异常面板

---

### 阶段 G：验证与收敛

**目标**：验证 v0.1 最小闭环是否成立。

**验证重点**：
- 首页是否帮助用户快速进入目标 agent
- 拓扑图是否帮助用户比聊天框更容易看懂结构
- 节点详情是否足以帮助用户理解最近状态与历史事件
- 当前实现是否仍保持 observer 边界

**完成标准**：
- 至少能用样例数据完成一次端到端演示
- 所有新增文档与实现术语保持一致

---

## 5. 测试与验证策略

第一阶段优先验证以下层次：

1. **契约验证**：最小字段结构是否一致
2. **页面渲染验证**：列表页与详情页是否能稳定渲染
3. **交互验证**：点击节点是否能打开正确详情面板
4. **样例数据验证**：典型 agent / subagent 树是否可正确展示

若当前仓库测试能力不完整，应先补齐最小可运行验证方式，再扩大自动化测试范围。

---

## 6. 暂不推进的实现项

以下实现项即便技术上可做，也不应在第一阶段提前推进：

- 多 agent 编排 UI
- 全局监控大盘
- 异常中心
- 控制按钮与 runtime 操作
- 资源监控
- 决策追溯视图
- 自定义垂域视图
- 与外部系统的大规模协议冻结

---

## 10. 清理后第一批执行块

### 执行块 1：后端最小 observer API

**目标**：基于纯内存 stub 数据交付 3 个只读接口。

**建议文件**：
- `app/domain/agent.py`
- `app/domain/node.py`
- `app/domain/event.py`
- `app/services/stub_data.py`
- `app/api/schemas.py`
- `app/api/agents.py`
- `app/main.py`
- `tests/integration/test_agents_api.py`

**完成标准**：
- `GET /agents` 返回最小列表
- `GET /agents/{agent_id}` 返回单 agent 详情与拓扑节点
- `GET /agents/{agent_id}/nodes/{node_id}` 返回节点详情与事件历史
- `tests/integration/test_health.py` 继续通过

**目标**：把当前中性 bootstrap 改造成可进入 observer 的最小前端入口。

**建议文件**：

- `frontend/src/api/client.ts`
- `frontend/src/components/AgentList.tsx`
- `frontend/src/components/AgentDetail.tsx`

**完成标准**：
- 首页显示 agents 列表

- 详情页展示 root + subagents 结构
- 点击节点打开右侧详情面板
- 面板展示当前状态、最近开始活跃时间与事件历史
