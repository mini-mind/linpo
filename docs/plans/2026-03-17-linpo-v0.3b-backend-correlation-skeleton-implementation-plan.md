# Linpo v0.3B Backend Correlation Skeleton Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在不进入前端控制 UI 的前提下，为 Linpo 建立 v0.3B 第一批后端最小控制请求状态模型与 observer 关联骨架，使至少一个控制动作具备 `accepted -> applied / timeout` 的可验证闭环。

**Architecture:** 基于现有 v0.3A operator 控制链路与 v0.2 realtime observer 基线，在后端新增最小 control request domain model，并把 OpenClaw 控制请求的 request id / action / agent 范围保留下来。同步控制回执继续表达“请求层状态”，最终 `applied` 必须由 observer realtime 流确认；若窗口内未确认，则收敛为 `timeout`。整个实现保持单实例、受信环境、单操作者边界，不引入前端 UI、多实例或更大控制台能力。

**Tech Stack:** FastAPI、Python、现有 OpenClaw websocket client、pytest、现有 realtime observer 测试基线。

## 2. 第一批后端 skeleton 范围

本计划只覆盖以下后端工作：

1. 新增最小控制请求状态模型：`sending / accepted / applied / failed / timeout`
2. 保留控制请求的最小关联信息：至少包含 `request_id`、`agent_id`、`action`
3. 允许后端对“控制请求已接受”与“observer 已确认生效”做区分
4. 为至少一个动作建立 `accepted -> applied` 或 `accepted -> timeout` 的最小状态流转
5. 区分控制请求错误与 observer 通道错误

本计划明确**不做**：

- 前端控制 UI 与前端状态渲染
- `send / pause / resume` 三个动作全集同时完善（第一批只要求至少一个动作可验证闭环）
- 多实例、多用户、长期审计、复杂补偿重试
- 完整 runbook/README 收敛

---

## 3. 设计约束

- `accepted` 不等于 `applied`
- `applied` 必须优先由 observer realtime 事件确认，而不是只靠同步 control API 返回值
- 若 observer 未在窗口内确认状态变化，请求必须进入 `timeout`，而不是静默保留为成功
- 若 control 请求本身失败，应保持 `failed`，且不能被 observer 通道状态伪装覆盖
- 若 observer 通道失败，应能与控制请求失败区分
- 实现应优先复用现有 `app/services/observer_data.py` 与 `app/api/realtime.py` 主链路，不新建第二套状态分发通道
- 只做单实例内存态 skeleton，不提前引入持久化仓库

## 4. 建议落点

### 4.1 控制请求域模型

**建议文件：**
- Create: `app/domain/control_request.py`
- Modify: `app/domain/__init__.py`（如当前包导出方式需要）

**建议内容：**
- `ControlRequestStatus` 枚举：`SENDING` / `ACCEPTED` / `APPLIED` / `FAILED` / `TIMEOUT`
- `ControlRequestRecord` 数据结构：
  - `request_id: str`
  - `agent_id: str`
  - `action: str`
  - `status: ControlRequestStatus`
  - `created_at: datetime`
  - `accepted_at: datetime | None`
  - `applied_at: datetime | None`
  - `error_code: str | None`
  - `error_message: str | None`
  - `correlation_hint: str | None`
- 只保留当前 v0.3B skeleton 必需字段，不提前扩展 runbook / 审计 / actor 信息

### 4.2 API / schema 契约

**建议文件：**
- Modify: `app/api/schemas.py`
- Modify: `app/api/agents.py`

**建议内容：**
- 扩展 `AgentControlStatus` 到 `sending / accepted / applied / failed / timeout`
- 扩展 `AgentControlResponse`，至少带出：
  - `request_id`
  - `status`
  - `correlation_hint`（可选，若现阶段只做 agent/action 级弱关联）
  - 现有 `message`
- `control_agent` 返回时应表达“请求层状态”，即：
  - 同步发送成功 -> `accepted`
  - 同步失败 -> `failed`
  - 同步等待超时 -> `timeout`
- **v0.3B 第一批的 HTTP 同步响应不得返回 `applied`；`applied` 仅允许由 observer realtime 流收敛确认。**
- 返回体必须为后续 observer-confirmed 收敛预留 `request_id` / correlation 信息

### 4.3 OpenClaw client / service

**建议文件：**
- Modify: `app/services/openclaw_client.py`

**建议内容：**
- 保留并暴露 `_next_control_request_id()` 生成的 request id
- `OpenClawOperatorService.send_action(...)` 不再只返回裸 `accepted/failed/timeout`，而是返回包含 request id 的最小记录或中间结果
- 对第一批动作优先继续使用当前 `pause -> chat.abort`
- `resume` 继续维持 `failed` 语义，不在本计划中提升
- 如需参考 OpenClaw 侧最小语义，可采用：
  - `req.id` 作为 transport correlation
  - `chat.abort` 的同步 `res` 作为 `accepted`
  - observer 侧目标事件作为 `applied`

### 4.4 observer 关联骨架

**建议文件：**
- Modify: `app/services/observer_data.py`
- Modify: `app/api/realtime.py`

**建议内容：**
- 在 `observer_data` 层新增最小 in-memory pending request registry
- registry 只处理当前单实例、单进程 skeleton：
  - 创建 pending record
  - 标记 accepted
  - 当 observer 事件满足弱关联条件时标记 applied
  - 在窗口超时后标记 timeout
- 第一批弱关联建议：
  - 按 `agent_id + action` 建立最小匹配
  - 若现有 observer event payload 可稳定暴露更具体字段，可附加 `correlation_hint`
- `app/api/realtime.py` 若当前会丢弃扩展 payload，应调整序列化，允许把最小 request-state / correlation 字段透出到 observer ws 事件中
- 不额外创建新的 websocket channel；继续复用现有 observer realtime 流

## 7. 风险与约束提醒

- 当前文档只冻结到“最小 correlation 语义”，未冻结精确关联键结构；实现应优先选最小弱关联，而不是发明复杂协议
- 若现有 observer 事件不足以稳定确认 `pause` 已应用，需要先把缺口显式记录出来，再决定是否提升关联条件；不要硬编码猜测语义
- 若要把 `runId` 引入本地契约，必须确认当前 Linpo 现有事件里确实可观测；否则先停留在 `agent_id + action + event type` 级弱关联
- 第一批不要求所有 API/WS 立刻完全一致地呈现 `applied`，但内部模型与 observer 关联骨架必须成立
- 发现需要新增持久化、跨进程状态共享或复杂补偿时，应停止实现并回到文档层
