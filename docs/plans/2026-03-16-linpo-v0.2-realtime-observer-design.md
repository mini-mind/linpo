# Linpo v0.2 Realtime Observer Design

> **状态**：提案草案（待确认后转为实施计划）
>
> **目标版本**：v0.2
>
> **前置约束**：`docs/prd/2026-03-15-linpo-v0.1-observer-prd.md`、`docs/architecture/2026-03-15-observer-architecture.md`

## 1. 文档目的

本文档用于定义 Linpo v0.2 的最小扩展方向：

> 在保持 observer-only 边界的前提下，把当前“按请求读取真实 OpenClaw 快照”的模型，扩展为“真实状态与拓扑的实时推送 + 短时事件缓冲”。

本文档不引入控制面、不引入完整历史回放系统，也不把 Linpo 扩张成运行编排平台。

---

## 2. v0.2 目标

v0.2 相对于 v0.1 的新增目标只有一类：

1. **列表页实时**：agent 状态与最近活跃时间可实时变化
2. **详情页实时**：单 agent 的拓扑与节点事件可实时变化
3. **短时缓冲**：浏览器短暂断线后可补回最近一小段增量事件
4. **失败回退**：若增量恢复失败，前端应回退到 HTTP 全量快照重同步

v0.2 仍然明确不做：

- 启动 / 暂停 / 恢复 / 重试 agent
- 任务控制
- 资源控制
- 完整事件回放
- 长期历史存储
- 用户直接连接 OpenClaw

---

## 3. 总体方案

### 3.1 桥接角色

Linpo 后端继续作为唯一桥接层：

- **上游**：Linpo 后端与 OpenClaw 保持长期连接，接收真实状态/拓扑/事件变化
- **中间层**：Linpo 后端维护当前内存态与短时 ring buffer
- **下游**：浏览器仅连接 Linpo 的 WebSocket 推送通道

前端不直接理解 OpenClaw 协议，也不持有 OpenClaw token。

### 3.2 兼容策略

v0.1 已存在的 3 个 HTTP 只读接口继续保留：

- `GET /agents`
- `GET /agents/{agent_id}`
- `GET /agents/{agent_id}/nodes/{node_id}`

它们在 v0.2 中承担：

- 首次页面加载快照
- WebSocket 断线后的重同步 fallback
- 手工排障入口
- 契约测试基线

WebSocket 只负责：

- 增量更新
- 短时缓冲补发
- 通知前端是否必须重拉快照

---

## 4. 推荐实时模型

### 4.1 采用模式

v0.2 采用：

> **快照 + 增量流 + 短缓冲补发 + 失效回退全量**

即：

- 正常情况下前端收到实时增量事件
- 若浏览器短暂断线，重连时带上上次已确认的 `last_seq`
- 后端若仍保有该段历史，则按序补发
- 若历史已过期或不可恢复，则后端返回 `resync_required`
- 前端随后重新调用 HTTP 接口拉全量快照，再继续订阅

### 4.2 为什么选这个方案

相较于“纯转发、断线直接丢”，该模型更适合观测 UI：

- 用户不会因为短暂网络抖动就完全丢失上下文
- 后端复杂度仍可控
- 不需要进入完整事件回放系统
- 与 Kubernetes `resourceVersion` / 观察者模式类似：**增量不可恢复时退回全量同步**

## 5. 后端设计

### 5.1 新增后端职责

Linpo 后端需要新增三个内部职责：

1. **OpenClaw 持续监听器**
   - 长期保持与 OpenClaw 的连接
   - 将上游变化转换为内部标准事件

2. **ObserverStateStore**
   - 保存当前列表页快照
   - 保存单 agent 当前拓扑快照
   - 保存节点最近事件视图

3. **ObserverEventBuffer**
   - 按频道维护短时 ring buffer
   - 为重连浏览器补发最近变更

### 5.2 建议频道

v0.2 先限制为两类频道：

- `agents:list`
  - 用于列表页 agent 摘要更新
- `agent:{agent_id}:detail`
  - 用于单 agent 的 topology 和 event 更新

不做全局“所有 agent 全量推送”频道，避免范围失控。

### 5.3 建议缓冲策略

初始建议：

- 每频道保留最近 `200~500` 条消息
- TTL `30~120` 秒
- 每条消息附带单调递增 `seq`

v0.2 只做**内存级**短缓冲，不引入 Redis / Kafka / 持久化事件仓库。

## 6. 前端设计

### 6.1 列表页

列表页行为：

1. 先通过 `GET /agents` 拉当前快照
2. 建立 `agents:list` WebSocket 订阅
3. 收到 agent 摘要变化后更新列表 UI
4. 若收到 `resync_required`，重新执行 `GET /agents`

### 6.2 详情页

详情页行为：

1. 先通过 `GET /agents/{agent_id}` 和 `GET /agents/{agent_id}/nodes/{node_id}` 获取当前快照
2. 建立 `agent:{agent_id}:detail` WebSocket 订阅
3. 接收拓扑变化和事件增量
4. 若收到 `resync_required`，重新拉详情页所需 HTTP 快照

### 6.3 UI 原则

v0.2 仍然保持 observer-only：

- 允许显示“实时中 / 已断线 / 重同步中”状态
- 允许在节点事件区显示实时追加事件
- 不增加任何控制按钮
- 不把实时事件面板扩张成完整日志控制台

---

## 7. 推送消息最小协议

### 7.1 通用字段

每条浏览器 WebSocket 消息建议至少包含：

- `type`
- `channel`
- `seq`
- `timestamp`
- `payload`

### 7.2 最小消息类型

v0.2 起步只需要：

- `snapshot_ready`
  - 订阅建立成功，后端确认频道状态
- `agent_summary_updated`
  - 列表页中的某个 agent 摘要发生变化
- `topology_updated`
  - 某个 agent 的 topology 结构或节点状态变化
- `node_events_appended`
  - 某个节点有新增事件
- `resync_required`
  - 缓冲失效，前端必须重新拉 HTTP 快照
- `error`
  - 只读通道自身出错

v0.2 不引入复杂 ACK 机制，只要求客户端保存 `last_seq`。

## 8. 错误与恢复策略

### 8.1 OpenClaw 上游失败

若 OpenClaw 长连接异常：

- 后端记录内部状态为“上游断开”
- 向对应浏览器频道发只读错误事件
- 前端只显示观测失败态，不提供修复按钮

### 8.2 浏览器重连

浏览器重连时：

- 携带该频道最近已应用的 `last_seq`
- 后端若仍保有区间历史，则补发缺失消息
- 若无法恢复，则发送 `resync_required`

### 8.3 契约约束

无论是否启用实时：

- 现有 3 个 GET 接口结构不变
- 缺失 agent / node 仍返回 `404`
- OpenClaw 错误仍显式暴露
- 不允许静默回退到 stub 伪装成功

---

## 9. 分阶段实施建议

### 阶段 A：后端状态与缓冲

- 定义内部标准事件
- 实现 `ObserverStateStore`
- 实现 `ObserverEventBuffer`
- 先不接浏览器，仅在后端内完成标准化状态流

### 阶段 B：浏览器 WebSocket 通道

- 新增浏览器 WebSocket endpoint
- 支持 `agents:list` / `agent:{agent_id}:detail`
- 支持 `last_seq` 重连恢复
- 支持 `resync_required`

### 阶段 C：前端实时订阅

- 列表页实时
- 详情页实时
- 增量更新 UI
- 断线重连提示与重同步流程

---

## 10. v0.2 完成标准

只有满足以下条件，才可认为 v0.2 完成：

1. 列表页可实时更新 agent 摘要
2. 详情页可实时更新 topology 与事件
3. 浏览器短暂断线后可恢复最近增量
4. 恢复失败时可安全回退到 HTTP 全量同步
5. 全程保持 observer-only，无控制面泄漏
6. OpenClaw 错误仍然显式暴露
