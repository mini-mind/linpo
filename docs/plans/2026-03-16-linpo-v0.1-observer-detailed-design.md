## 1. 文档目的

本文档用于把已经冻结的 observer 方向继续细化到“可以直接开始实现”的粒度。

当前仓库已完成对 v0.0 辩论 demo 的激进清理，只保留了最小前后端 bootstrap 与健康检查。因此，本设计直接面向一个干净基座，不再假设旧代码可复用。

本文档只覆盖第一批最小实现切片：

- agents 列表页
- 单个 agent 详情页
- 完整拓扑图
- 节点详情侧栏
- 最小事件历史

---

## 2. 第一批最小闭环

第一批实现只证明一件事：

> 用户是否能通过列表页与拓扑页，比聊天框更容易看懂一个 agent / subagent 系统。

因此第一批闭环定义为：

1. 后端提供最小 stub 数据
2. 后端提供 observer 读取接口
3. 前端能显示 agents 列表
4. 前端能进入单个 agent 详情页
5. 前端能渲染完整拓扑
6. 前端点击节点后能看到最小详情面板与事件历史

这一闭环内明确不做：

- 登录系统
- 写操作
- 控制操作
- 协议对接
- 资源监控
- 告警/异常中心
- 聊天式交互

---

## 3. 后端最小数据契约

### 3.1 Agents 列表项

用于 `/agents` 返回值。

```ts
interface AgentListItem {
  id: string;
  name: string;
  status: 'idle' | 'running' | 'finished' | 'error';
  is_active: boolean;
  last_active_at: string | null;
}
```

字段说明：
- `id`：进入详情页所需唯一标识
- `name`：列表主显示字段
- `status`：当前状态
- `is_active`：当前是否活跃
- `last_active_at`：最近活跃时间，用于列表页展示

### 3.2 拓扑节点

用于 `/agents/{id}` 详情响应中的节点集合。

```ts
interface TopologyNode {
  id: string;
  name: string;
  status: 'idle' | 'running' | 'finished' | 'error';
  is_active: boolean;
  child_count: number;
  parent_id: string | null;
}
```

字段说明：
- `child_count`：节点本体展示所需
- `parent_id`：前端重建父子结构所需

### 3.3 Agent 详情响应

```ts
interface AgentDetailResponse {
  id: string;
  name: string;
  status: 'idle' | 'running' | 'finished' | 'error';
  is_active: boolean;
  child_count: number;
  last_active_at: string | null;
  nodes: TopologyNode[];
}
```

### 3.4 事件记录

用于节点详情面板。

```ts
interface EventRecord {
  id: string;
  node_id: string;
  type:
    | 'agent_created'
    | 'subagent_created'
    | 'activity_started'
    | 'activity_stopped'
    | 'status_changed'
    | 'node_finished'
    | 'task_started'
    | 'task_finished'
    | 'task_interrupted';
  timestamp: string;
  description: string;
}
```

### 3.5 节点详情响应

```ts
interface NodeDetailResponse {
  id: string;
  name: string;
  status: 'idle' | 'running' | 'finished' | 'error';
  is_active: boolean;
  last_active_started_at: string | null;
  events: EventRecord[];
}
```

## 4. 后端接口切片

第一批只提供 3 个只读接口：

| 方法 | 路径 | 作用 |
|------|------|------|
| `GET` | `/agents` | 获取 agents 列表 |
| `GET` | `/agents/{agent_id}` | 获取单个 agent 的详情与拓扑 |
| `GET` | `/agents/{agent_id}/nodes/{node_id}` | 获取节点详情与事件历史 |

当前不单独拆 `/events` 端点，避免第一批 API 面过宽。事件直接内嵌在节点详情中。

---

## 5. 后端实现结构

建议第一批采用纯内存 stub，不引入数据库或复杂 repository 层。

### 5.1 建议文件

- `app/domain/agent.py`
- `app/domain/node.py`
- `app/domain/event.py`
- `app/services/stub_data.py`
- `app/api/schemas.py`
- `app/api/agents.py`
- `app/main.py`

### 5.2 stub 数据原则

至少提供 2 个 agent：

- 一个有 subagents 的 agent
- 一个没有 subagents 的 agent

这样可以同时覆盖：
- 列表页多条数据
- 详情页拓扑结构
- 单节点与多节点两种情况

### 5.3 非目标

当前后端不做：
- repository
- database
- 鉴权
- runtime 同步
- websocket 推送
- 持久化事件流

---

## 6. 前端页面骨架

第一批前端只需要两个顶层页面：

- `/` 或 `/agents`：agents 列表页
- `/agents/:agentId`：agent 详情页

建议引入最小路由能力，使用单页应用实现页面切换。

---

## 7. 前端组件拆分

### 7.1 AgentsListPage

职责：
- 获取 agents 列表
- 以纯列表形式展示
- 点击进入 agent 详情页

展示字段：
- 名称
- 状态
- 是否活跃
- 最近活跃时间

明确不做：
- 搜索
- 筛选
- 仪表盘
- 状态聚类
- 批量操作

### 7.2 AgentDetailPage

职责：
- 获取单个 agent 详情
- 展示拓扑图
- 管理当前选中节点
- 展示节点详情侧栏

页面结构：
- 返回列表入口
- agent 标题区
- 主内容区：拓扑图
- 右侧：节点详情侧栏

### 7.3 TopologyTree / TopologyCanvas

职责：
- 渲染完整拓扑结构
- 用父子关系展示 root 与 subagents
- 支持点击节点

第一版建议使用最简单树形渲染，而不是复杂图引擎。原因：
- 当前目标是结构可见性
- 不是布局算法演示
- 树形渲染更容易快速验证

### 7.4 NodeCard

节点只显示：
- 名称
- 状态
- 是否活跃
- 子节点数

不显示：
- 任务摘要
- token
- 资源
- 错误详情
- 事件摘要

### 7.5 NodeDetailPanel

展示：
- 名称
- 当前状态
- 当前是否活跃
- 最近开始活跃时间
- 历史事件列表

不展示：
- 控制按钮
- 资源数据
- 任务卡片
- 决策摘要
- 告警分级

## 9. 第一批实现顺序

### 阶段 A：后端最小模型与 stub 数据

1. 定义 `AgentStatus`
2. 定义 `Agent`
3. 定义 `TopologyNode`
4. 定义 `EventRecord`
5. 写 stub 数据服务

### 阶段 B：后端 observer API

1. 写响应 schema
2. 写 `GET /agents`
3. 写 `GET /agents/{agent_id}`
4. 写 `GET /agents/{agent_id}/nodes/{node_id}`
5. 把 router 注册到 `app/main.py`

### 阶段 C：后端测试

1. 新建 `tests/integration/test_agents_api.py`
2. 验证列表返回
3. 验证详情返回
4. 验证节点详情返回
5. 保持旧 `/health` 测试通过

### 阶段 D：前端基础路由与 API client

1. 增加前端路由依赖
2. 写 `frontend/src/api/client.ts`
3. 改造 `frontend/src/main.tsx`
4. 接入列表页路由
5. 接入详情页路由

### 阶段 E：列表页

1. 渲染 agents 列表
2. 支持点击进入详情页
3. 显示最小字段

### 阶段 F：详情页与拓扑图

1. 获取详情数据
2. 渲染树形拓扑
3. 实现节点点击
4. 管理选中态

### 阶段 G：节点详情侧栏

1. 获取节点详情
2. 渲染状态字段
3. 渲染事件历史
4. 支持面板关闭

### 阶段 H：前端验证

1. `npm run build`
2. 最小前端测试
3. 手动串通列表 → 详情 → 节点侧栏主路径

## 10. 最小验证标准

第一批实现完成时，至少需要满足：

### 后端
- `GET /health` 返回 200
- `GET /agents` 返回 200 且至少 2 个 agent
- `GET /agents/{id}` 返回拓扑数据
- `GET /agents/{id}/nodes/{node_id}` 返回节点详情数据

### 前端
- 首页能显示 agents 列表
- 点击 agent 能进入详情页
- 详情页能显示 root + subagents 结构
- 点击节点能打开右侧详情面板
- 面板能显示事件历史

### 边界
- 不引入控制能力
- 不引入聊天框
- 不引入告警中心
- 不引入资源监控

---

## 11. 当前明确不做

以下内容即使容易顺手实现，也不应进入第一批：

- 多 agent 团队页
- 登录体系
- 真实接入协议
- 实时流更新
- 拖拽拓扑布局
- 智能高亮路径
- 节点搜索
- 分页
- 排序器
- 复杂 UI 主题系统
- 持久化存储
- 复杂测试基建

---

## 12. 与后续任务分派的关系

从任务委派角度，当前最适合拆成 3 个实现块：

1. **后端最小 observer API**
2. **前端列表页 + 路由骨架**
3. **前端详情页 + 拓扑图 + 节点详情侧栏**

其中：
- 后端块可先独立完成并验证
- 前端列表页可在后端接口明确后并行推进
- 详情页块依赖后端详情契约与前端路由骨架，但仍可独立实现

因此，下一轮最适合采用“按实现块串行推进、块内细任务明确”的 subagent 协作方式。
