# Linpo v0.1 Observer Design

> **For Claude:** This document captures validated product design consensus for Linpo v0.1. Do not start implementation until product, architecture, and phase documents are aligned.

**Goal:** 将 Linpo 从当前用于方向验证的 v0.0 辩论 demo，收敛为一个可被继续实现的 v0.1 产品设计：面向人类的单 agent（含 subagents）运行观测入口。

**Architecture:** v0.1 不把 Linpo 定义为 agent runtime、编排平台或任务系统，而是定义为观测者。用户登录后先看到自己的 agents 列表，再进入单个 agent 的详情页，通过完整拓扑图与极简节点详情理解 agent / subagent 的结构与运行状态。

**Tech Stack:** 暂不冻结实现技术方案；当前文档只冻结产品角色、信息架构、最小状态模型与演进边界。

---

## 1. 文档目的

本文档用于冻结 Linpo v0.1 的产品设计共识，作为后续更新 PRD、架构文档与实现计划的前置输入。

本文档不直接替代当前 `docs/prd/2026-03-12-linpo-v0.1.md` 中仍然有效的已落盘事实，而是明确指出一个新的产品方向：

- 当前仓库中的辩论赛 demo 应被重新理解为 **v0.0 验证载体**
- 真正的 `Linpo v0.1` 应重新定义为 **单 agent（含 subagents）运行状态监控产品**
- 在 v0.1 中，Linpo 扮演 **观测者**，而不是控制者

在对应 PRD 与架构文档完成更新前，不应直接按本文档开始复杂实现。

---

## 2. 版本分层

### 2.1 v0.0：方向验证 demo

当前仓库中的“多 OpenClaw 结构化辩论”闭环，应视为 Linpo 的 `v0.0`：

- 它的作用是验证方向，而不是定义长期产品形态
- 它证明了多 agent 参与、主持人视角、过程外显、结构化复盘等交互语法具有潜力
- 它不应继续被当作 Linpo 长期产品定义本身

### 2.2 v0.1：单 agent 运行观测入口

Linpo `v0.1` 的目标应收敛为：

> 面向人类提供一个单 agent（含 subagents）运行状态的结构化观测入口，以替代聊天框这种线性交互方式。

这里的重点不是多 agent 编排，也不是任务自动化，而是先证明：

- agent 可以被当成一个结构化对象来理解
- 人类能够通过图形化界面而不是聊天流掌控全局
- subagents 的存在不再被隐藏在线性输出之后

---

## 3. 产品定位

Linpo v0.1 应被定义为一个面向人类的 **agent 运行观测入口**。

它不是：

- agent runtime
- 通用编排平台
- 任务系统
- 资源监控平台
- 对话增强器
- 完整运维控制台

它首先是一个新的交互入口，试图解决聊天框在 agent 管理场景下的几个天然问题：

- 聊天框是线性的，难以表达层级结构
- 当 agent 派生 subagents 时，人类难以持续维持全局认知
- 对话式输出更适合消费结果，不适合管理系统结构
- 管理者必须投入额外脑力，把线性叙事重新还原成运行结构

Linpo v0.1 的产品价值，在于把这些隐性结构直接外显出来。

---

## 4. 核心用户视角

v0.1 当前不预先锁定某一个狭窄垂域，也不把自己限制为开发者工具。

当前共识是：

- 先以 **通用入口** 为产品站位
- 先抽象出 agent 运行观测这一通用能力
- 后续再决定是否向特定垂域、管理角色或更强控制面演进

但即便保持通用入口定位，v0.1 的核心用户行为仍然非常清楚：

- 用户登录系统
- 查看自己拥有的 agents
- 进入某个 agent
- 看清这个 agent 与其 subagents 的结构
- 理解哪些节点在运行、何时活跃过、经历了什么事件

因此，v0.1 的第一目标不是让用户“操作 agent”，而是让用户“看懂 agent”。

---

## 5. v0.1 的产品角色：观测者

在 v0.1 中，Linpo 的角色明确是 **观测者（Observer）**。

这意味着：

- Linpo 先不负责启动 agent
- 先不负责暂停 / 恢复 / 重试
- 先不负责编排 subagents
- 先不负责调度任务优先级
- 先不负责统一生命周期控制

换句话说，v0.1 不抢 agent runtime 的控制权。

Linpo 只做一件事：

> 把 agent 及其 subagents 的结构和状态变成可见、可浏览、可回看的对象。

这个边界是有意收窄的，因为只有先把“看清楚”这件事做好，后续控制、编排、追责、资源治理等能力才有稳定落点。

---

## 6. 信息架构

### 6.1 顶层入口

用户登录后，首先进入 **agents 列表页**。

列表页只承担两个职责：

- 让用户知道自己有哪些 agents
- 让用户进入某一个 agent 的详情页

它不承担：

- 总控大盘
- 复杂分析
- 异常中心
- 资源监控仪表盘
- 编排入口

### 6.2 主对象

v0.1 的主对象是 **Agent**。

这意味着产品的第一认知单位不是 task、run、session 或 workspace，而是 agent 本身。

原因是：

- “单个 agent（含 subagents）状态监控”是 v0.1 已冻结的切入口
- Agent 是最稳定的入口对象
- task / run / session 更适合作为未来演进出来的二级或三级视角

### 6.3 Agent 详情页

点击某个 agent 后，进入该 agent 的详情页。

详情页的中心是：

> **完整的 Agent / Subagent 拓扑图**

这个拓扑图是 v0.1 的第一核心视图，也是与聊天框形成显著差异的关键交互。

---

## 7. 第一核心视图：Agent / Subagent 拓扑图

v0.1 的第一核心视图应采用 **完整拓扑展示**。

当前共识是：

- 默认展示完整结构
- 不做“当前活跃路径”高亮
- 不做“最近变化节点”高亮
- 不做复杂聚焦逻辑
- 不引入智能推荐或自动摘要

原因很简单：

- v0.1 要先证明结构可见性本身成立
- 不应让第一版被智能聚焦逻辑反向绑架
- 用户需要的是一个稳定、清晰的结构视图，而不是过度加工后的解释层

因此，拓扑图在 v0.1 中首先是一张“结构图”，而不是“决策图”“资源图”或“监控图”。

---

## 8. 节点设计

### 8.1 极简节点原则

拓扑图中的节点应保持极简。

每个节点只展示：

- 名称
- 状态
- 是否活跃
- 子节点数

这里故意不把更多字段堆进节点本体，例如：

- 当前任务摘要
- token 消耗
- 错误分类
- 资源占用
- 最近事件
- 运行时配置

因为第一版拓扑图的核心目标是让用户先看清结构，而不是在图上直接消费所有细节。

### 8.2 详情后置

更多信息通过点击节点后展开的详情面板承接。

这个设计原则可以概括为：

> 结构优先，细节后置。

---

## 9. 节点详情面板

点击任一节点后，Linpo 应展示一个侧边详情面板。

在 v0.1 中，该面板只展示最少必要的状态信息：

- 最近开始活跃的时间点
- 当前是否活跃
- 历史事件记录

当前共识是：

- 不在 v0.1 中加入任务详情卡片
- 不加入资源面板
- 不加入控制按钮
- 不加入决策摘要
- 不加入异常分类与告警面板

这样做的目的，是保证 v0.1 的详情面板仍然服务于“状态理解”，而不是开始承担一个完整控制台的职责。

---

## 10. 状态与事件模型

### 10.1 最小状态模型

在 v0.1 中，每个 agent 节点至少需要被表达为一个可观测的运行节点，拥有以下稳定字段：

- 名称
- 当前状态
- 是否活跃
- 子节点数

这里的“状态”在 v0.1 阶段不承担复杂告警语义。

当前共识是：

- 异常暂不作为首页和拓扑层的一等状态
- v0.1 不把自己做成告警中心或运维监控台
- 即便存在异常，也可先作为事件记录的一部分体现

### 10.2 最小事件模型

v0.1 需要一套支撑详情面板的最小事件模型。

#### 结构 / 状态事件

- agent 创建
- subagent 创建
- 开始活跃
- 停止活跃
- 状态变化
- 节点结束

#### 最小任务边界事件

- 任务开始
- 任务结束
- 任务中断

这个事件模型的作用，不是把 Linpo 变成任务系统，而是帮助用户回答：

- 这个节点何时开始工作
- 这个节点何时结束工作
- 一段活跃期对应了哪些最小工作边界
- 在此期间发生了哪些结构和状态变化

---

## 11. 首页：Agents 列表页

v0.1 的 agents 列表页应采用 **纯列表** 形式。

每个 agent 一行，仅展示：

- 名称
- 当前状态
- 是否活跃
- 最近活跃时间

当前共识是：

- 不使用卡片网格作为默认布局
- 不在首页加入复杂仪表盘
- 不按异常做显式优先分组
- 列表页只作为“发现与进入”的入口

换句话说，列表页的价值不在“展示产品野心”，而在“快速进入目标 agent”。

---

## 12. 成功标准

Linpo v0.1 的首要成功标准不是控制能力，不是诊断能力，也不是自动化能力。

当前已冻结的首要成功标准是：

> 用户第一次进入后，能比聊天框更容易看懂一个 agent / subagent 系统的结构。

这意味着 v0.1 的验证重点应放在以下问题上：

- 用户是否能一眼分辨根 agent 与 subagents 的关系
- 用户是否能知道系统当前是否还在运行
- 用户是否能知道某个节点最近是否活跃过
- 用户是否能通过历史事件理解节点经历过什么

只要这个目标成立，Linpo 就已经从“验证 demo”迈入了“新的交互入口”。

---

## 13. 明确不做

为避免 v0.1 失焦，以下能力在当前版本明确不做：

- 多 agent 编排
- 统一 runtime 控制
- 暂停 / 恢复 / 重试等控制操作
- 复杂任务系统
- 决策点追溯视图
- 资源监控视图
- 全局异常中心
- 用户 DIY 垂域视图
- 接入协议冻结

这些能力可以作为未来版本的扩张方向，但都不应成为 v0.1 的前置条件。

---

## 14. 后续演进边界

如果 v0.1 的“结构可见性”被验证成立，Linpo 才有资格继续向后演进。

后续可考虑的能力包括：

- 任务进度视图
- 关键决策点追溯视图
- 资源监控视图
- 异常上浮与告警
- 轻量控制能力
- 用户自定义垂域视图
- 更强的多 agent 团队管理视图

但这些都应建立在一个前提之上：

> v0.1 已经证明，agent 管理入口本身成立。
