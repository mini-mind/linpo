# Linpo v0.3 Single Agent Control Plan

> **状态**：草案（待确认后进入实现计划）
>
> **目标版本**：v0.3
>
> **前置约束**：`docs/prd/2026-03-15-linpo-v0.1-observer-prd.md`、`docs/architecture/2026-03-15-observer-architecture.md`、`docs/plans/2026-03-16-linpo-v0.2-realtime-observer-implementation-plan.md`

## 1. 文档目的

本文档用于定义 Linpo 从 v0.2 realtime observer 进入 v0.3 的最小扩展方向：

> 在保持“单实例、受信环境、单操作者验证”边界的前提下，把当前 observer-only 入口扩展为“可发起最小控制请求，并能通过 realtime observer 看到状态反馈”的控制接入闭环。

本文档不引入多用户隔离，不引入多实例聚合，不引入完整控制台，也不把 Linpo 变成新的 runtime 编排平台。

---

## 2. v0.3 的版本定位

v0.3 不是“单实例控制能力全部做完”，而是一个**控制接入验证阶段**。

它只回答两个问题：

1. Linpo 能否以 `operator` 角色安全接入 OpenClaw 的最小控制协议？
2. 控制请求能否与现有 realtime observer 视图形成可理解、可验证的最小闭环？

如果这两个问题不能成立，就不应继续进入更完整的单实例控制、用户模型或多实例平台化阶段。

---

## 3. v0.3 进入条件

只有满足以下条件，Linpo 才应推进 v0.3：

1. `agents:list` 与 `agent:{agent_id}:detail` 的 realtime 主路径已稳定
2. `last_seq` / `resync_required` / 上游失败显式暴露已作为既有契约存在
3. v0.2 observer-only 范围已收口，不再继续叠加新的观测语义
4. 控制接入仍限定在**单实例、受信环境、单操作者**，不承诺多用户隔离
5. OpenClaw 的 operator / scopes / device pairing 最小接入前置已被文档化

---

## 4. v0.3 最小交付目标

v0.3 只交付以下能力：

1. Linpo 后端可使用 `operator` 角色与 OpenClaw 建立最小受控连接
2. 设备身份与 pairing 流程可完成最小验证，并对失败给出明确错误语义
3. Linpo 前端可对单个 agent 发起最小控制动作
4. 前端可区分以下状态：
   - 请求发送中
   - 请求被上游接受
   - 状态已通过 observer 流体现
   - 请求失败 / 超时
5. 全程保持单实例边界，不引入用户系统、多实例聚合或共享权限模型

v0.3 明确不做：

- 多用户登录/实例授权
- 多实例控制
- 完整 agent 管理台
- 完整 chat 控制台
- 跨实例消息路由
- 长期操作审计仓库

---

## 5. 推荐拆解：v0.3A / v0.3B

### 5.1 v0.3A：控制协议接入验证

目标：先证明 Linpo 能以 `operator` 身份接入 OpenClaw 的最小控制协议。

本阶段只关注：

- `role=operator` 的显式接入
- `scopes` 的最小声明
- `device` 身份参数的组织与签名输入
- pairing 的最小成功 / 失败路径
- 至少一个最小写请求可被安全发出并拿到明确回执

v0.3A 的完成标准：

1. 后端可以显式区分 observer / operator 两种接入角色
2. pairing 成功与失败有明确错误语义，不静默回退
3. 至少一个最小控制请求可跑通完整链路
4. 不要求前端已有完整控制 UI

### 5.2 v0.3B：最小控制闭环

目标：让 Linpo UI 能发起最小控制动作，并通过 realtime observer 看到状态变化。

本阶段建议优先动作集：

- `send`
- `pause`
- `resume`

`start` 与更复杂的管理动作建议后置到 v0.4，除非 OpenClaw 侧语义已足够稳定。

v0.3B 的完成标准：

1. 用户可以对单个 agent 发起最小控制动作
2. UI 中可以区分“请求已发出”与“状态已生效”
3. 状态生效应优先通过 observer realtime 流确认，而不是只靠同步请求返回值
4. 超时、失败、上游异常应有显式反馈，不伪装成功

---

## 6. 控制面与观测面的协同约束

v0.3 的核心不是“多几个按钮”，而是建立**控制请求 ↔ realtime observer 反馈**的最小闭环。

因此必须遵守以下约束：

1. 控制请求返回“accepted”，不等于状态已经生效
2. 真正的状态确认应优先来自现有 observer realtime 流
3. 若控制请求成功返回，但 observer 流在窗口内未体现状态变化，UI 应显示超时/待确认，而不是直接宣称成功
4. 若 observer 流先于同步请求回执体现变化，前端仍需保持状态一致性，不重复渲染成功语义
5. 控制请求错误与 observer 通道错误必须区分，避免把“控制失败”误判成“观测失败”

---

## 7. 建议前后端最小分工

### 7.1 后端

v0.3 后端新增职责：

- operator 角色接入与最小握手
- device pairing 参数组织与错误暴露
- 单 agent 控制请求转发
- 控制请求与 observer 状态流之间的关联标识（最小 correlation 语义）

### 7.2 前端

v0.3 前端新增职责：

- 单 agent 最小控制入口
- 控制请求状态展示（sending / accepted / applied / timeout / failed）
- 与既有 realtime observer 状态融合展示
- 错误提示与最小重试入口

---

## 8. 分阶段实施建议

### 阶段 A：协议与失败语义冻结

- 明确 `operator` / `scopes` / `device pairing` 的最小契约
- 定义成功、拒绝、配对失败、超时的错误口径
- 明确控制请求与 observer 状态确认的关系

### 阶段 B：后端 operator 接入

- 实现 observer / operator 角色分流
- 实现 pairing 最小链路
- 打通至少一个最小控制请求
- 保证失败时显式暴露

### 阶段 C：前端最小控制 UI

- 在单 agent 详情页接入最小控制动作
- 增加请求中 / 已接受 / 已生效 / 失败 / 超时状态
- 保持界面最小化，不扩张成控制台

### 阶段 D：联调与回归验证

- 验证控制请求成功路径
- 验证 observer 流确认路径
- 验证 pairing 失败 / 请求失败 / 超时 / 上游异常
- 验证现有 v0.2 realtime observer 主路径不被破坏

---

## 9. v0.3 完成标准

只有同时满足以下条件，才可认为 v0.3 完成：

1. 已打通 `operator` 最小接入链路
2. pairing 成功 / 失败路径已验证
3. 至少一个最小控制动作可从 UI 发起并完成端到端链路
4. UI 可区分请求状态与实际生效状态
5. observer realtime 主路径继续稳定存在
6. 全程保持单实例、受信环境、单操作者边界

---

## 10. 与 v0.4 的边界

以下内容即便技术上可做，也不应在 v0.3 提前推进：

- 完整控制动作全集
- 完整 Agent 管理 UI（bindings / 全量管理）
- 复杂失败补偿与重试策略
- 多实例控制
- 用户登录与实例授权模型
- 安全审计与长期操作记录

这些能力属于 v0.4 及之后的范围。
