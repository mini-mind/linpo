# Linpo v0.3 Single Agent Control Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在保持单实例、受信环境、单操作者验证边界的前提下，为 Linpo 交付“operator 接入 + 最小控制动作 + realtime observer 状态确认”的 v0.3 控制接入闭环。

**Architecture:** 基于现有 v0.2 realtime observer 基线，后端新增 operator 角色接入、device pairing 与最小控制请求转发；前端在单 agent 详情页增加最小控制入口，并通过既有 realtime observer 通道消费 OpenClaw 当前协议允许的真实确认信号。控制请求返回值只表达协议已确认的结果，不再把同步回执、猜测状态或旧字段兼容逻辑误当成真实状态。

**Tech Stack:** FastAPI、Python websockets client、React、TypeScript、Vite、pytest、前端现有测试脚本。

## 2. v0.3 最小交付目标

本阶段只交付一个最小控制接入闭环：

1. 后端可用 `operator` 角色接入 OpenClaw 的最小控制协议
2. device pairing 的成功 / 失败路径可显式验证
3. 单 agent 可发起最小控制动作，建议优先 `send` / `pause` / `resume`
4. 前端可区分“请求发送中 / 已接受 / 已生效 / 失败 / 超时”
5. 状态是否真正生效，优先通过现有 realtime observer 通道确认
6. v0.2 realtime observer 主路径继续稳定存在，不因控制面引入而退化
7. 全程保持单实例、受信环境、单操作者验证边界

如果以上 7 点不能同时成立，就不应继续扩张到完整控制动作全集、单实例 Agent 管理台、多用户模型或多实例控制。

## 3. 实施原则

- 先冻结 operator / scopes / pairing / 失败语义，再写控制代码
- OpenClaw 当前协议是唯一真源：字段名、事件名、状态流转、sessionKey 语义都必须以当前官方协议与 Control UI 实现为准
- 不做向后兼容，不保留旧 Linpo 假设字段，不允许 fallback 或兜底分支
- 先打通后端最小控制链路，再接前端 UI
- 先验证一个最小动作集，再扩张动作全集
- 控制请求的同步回执只表达“请求状态”，不直接等价于“真实系统状态”
- 真实状态确认优先复用既有 observer realtime 流，不另造第二套状态源
- 保持 YAGNI：v0.3 不引入多用户认证、多实例路由、长期审计仓库或复杂补偿系统

## 4. 阶段拆解

### 阶段 A：文档与最小控制契约冻结

**目标**：把 v0.3 从控制接入草案收敛为可执行计划，并冻结 operator / pairing / 请求回执 / observer 状态确认之间的最小契约。

**交付物**：
- 本实施计划文档
- 控制动作最小集合定义（建议：`send` / `pause` / `resume`）
- pairing 成功、失败、超时、拒绝四类错误口径
- 前后端共享的最小控制请求状态枚举

**完成标准**：
- `docs/plans/2026-03-17-linpo-v0.3-single-agent-control-plan.md` 与本计划对阶段、动作集、边界表述一致
- 明确同步请求只表达 `sending/accepted/failed/timeout` 一类语义
- 明确最终状态确认优先来自 observer realtime 流
- 明确 v0.3 不纳入 `start` 的前提条件，除非上游语义已稳定并被重新文档化

---

### 阶段 B：后端 operator 接入与 pairing 链路

**目标**：在不破坏现有 observer-only / realtime 主路径的前提下，为后端补齐 operator 角色接入、device pairing 与最小控制请求通路。

**需要实现的能力**：
- 在 OpenClaw client / data source 层显式区分 observer 与 operator 角色
- 支持 operator 角色所需的 `role` / `scopes` / `device` 参数
- 实现 device pairing 的最小成功 / 失败 / 超时语义
- 提供单 agent 最小控制请求的服务层入口
- 保持 realtime observer 状态流仍可独立工作

**完成标准**：
- 后端可显式完成 operator 最小握手
- pairing 失败不会静默回退到 observer 或 stub
- 至少一个最小控制请求可跑通端到端链路并返回明确回执
- v0.2 realtime 相关测试基线继续通过

---

### 阶段 C：控制请求状态模型与 observer 关联

**目标**：让后端能表达“请求已发出”与“状态已生效”的区别，并建立最小 correlation 语义，避免前端把同步回执当成最终状态。

**需要实现的能力**：
- 为控制请求定义最小状态模型：`sending` / `accepted` / `applied` / `failed` / `timeout`
- 对每个动作明确“同步协议结果”与“异步 observer 确认”的边界，不能发明额外状态语义
- pause 路径必须严格遵从 OpenClaw `chat.abort` 当前协议：请求参数使用真实 `sessionKey`，同步响应必须检查 `payload.aborted` 与 `runIds`
- 为请求与后续 observer 事件之间建立最小关联标识，并优先使用协议内已有键（如 `sessionKey` / `runId`），而不是本地猜测字段
- 定义在 observer 流未确认状态变化时的超时策略
- 区分控制请求错误与 observer 通道错误

**完成标准**：
- 后端单元测试能证明请求状态流转成立
- 至少一个动作可以从 `accepted` 进入 `applied`，且 `applied` 由 OpenClaw 当前协议中真实存在的 observer 事件确认
- 若上游协议同步响应已经明确动作未生效，则系统必须直接返回 `failed`，不得先标记 `accepted` 再等待超时
- observer 流未确认时，系统能进入 `timeout` 或“待确认失败”语义

---

### 阶段 D：前端单 agent 最小控制 UI

**目标**：在现有 agent 详情页中接入最小控制动作入口与请求状态反馈，不扩张成完整控制台。

**需要实现的能力**：
- 在 `AgentDetail` 或其子组件中增加最小控制入口
- 对 `send` / `pause` / `resume` 显示最小按钮或输入控件
- UI 上可展示：`sending` / `accepted` / `applied` / `failed` / `timeout`
- 当 observer 流确认状态变化时，收敛为“已生效”状态
- 若 observer 流未确认，则在窗口后显示超时或待确认失败

**完成标准**：
- 前端 build 与现有测试通过
- 新增前端测试可证明请求状态渲染与 observer 状态收敛逻辑成立
- 不增加多实例入口、用户权限 UI 或完整聊天控制台

---

### 阶段 E：联调与回归收敛

**目标**：证明 v0.3 的最小控制闭环成立，并且没有破坏 v0.2 realtime observer 主路径。

**必须覆盖的验证场景**：
1. operator 最小握手成功
2. pairing 失败被显式暴露
3. 最小控制动作发送成功并收到 accepted
4. observer realtime 流确认状态变化，UI 转为 applied（仅当 OpenClaw 当前协议真实提供确认事件）
5. observer 未确认时进入 timeout / 待确认失败
6. 上游异常时控制错误与观测错误可区分
7. 既有列表页 / 详情页 realtime 主路径继续可用

**完成标准**：
- 自动化测试覆盖关键请求状态与失败路径
- 运行说明可指导一次本地或联调演示
- 文档、API、UI 文案中的请求状态术语保持一致

---

## 5. 推荐实现顺序

1. 先冻结最小控制动作集与状态枚举
2. 再做后端 operator 接入与 pairing 失败语义
3. 再做控制请求状态模型与 observer 关联
4. 再接前端单 agent 最小控制 UI
5. 最后补联调说明与回归验证

## 6. 第一批执行块

### 执行块 1：后端 operator client 与 pairing 骨架

**目标**：在后端补齐 operator 角色所需的最小 client / service 基础设施，但暂不接前端 UI。

**建议文件**：
- `app/services/openclaw_client.py`
- `app/services/observer_data.py`（如需复用现有数据源组织）
- `app/domain/` 下新增或扩展控制请求 / pairing / 请求状态相关模型
- `tests/` 下新增 operator / pairing 相关单元测试

**完成标准**：
- 可显式创建 observer / operator 两类连接路径
- 可组织最小 `device` / `scopes` 输入
- pairing 成功 / 失败 / 超时语义具备测试覆盖
- 不破坏既有 observer-only 路径

### 执行块 2：后端控制请求服务层

**目标**：交付单 agent 最小控制请求入口与明确回执模型。

**建议文件**：
- `app/api/agents.py` 或新增控制相关 API 路由文件
- `app/api/schemas.py` 或新增控制请求 / 响应 schema 文件
- `app/services/openclaw_client.py`
- `tests/integration/` 下新增控制请求相关集成测试

**完成标准**：
- 至少支持一个最小动作集的后端请求入口
- 返回值可区分 `accepted` / `failed` / `timeout`
- pairing 未完成或 operator 接入失败时显式报错
- 不把同步回执伪装成真实状态生效

### 执行块 3：请求状态模型与 observer 关联

**目标**：让控制请求回执与 observer 状态变化形成最小可验证闭环。

**建议文件**：
- `app/services/observer_data.py`
- `app/domain/` 下控制状态 / 关联标识模型文件
- `tests/test_*` 或 `tests/integration/` 下新增状态流转测试

**完成标准**：
- 至少一个动作支持 `accepted -> applied`
- `applied` 必须由 observer realtime 事件驱动确认
- observer 未确认时能进入 `timeout`
- 控制错误与 observer 通道错误可区分

### 执行块 4：前端单 agent 控制入口

**目标**：在现有详情页最小接入控制动作与状态反馈。

**建议文件**：
- `frontend/src/api/client.ts`
- `frontend/src/components/AgentDetail.tsx`
- `frontend/src/components/NodeDetailPanel.tsx`（如需展示关联状态）
- 如有必要，新增 `frontend/src/components/AgentControls.tsx`
- `frontend/src/api/` 下新增控制请求桥接逻辑
- `frontend/src/components/*.test.tsx` 下新增最小控制 UI 测试

**完成标准**：
- UI 可触发最小控制动作
- UI 可展示 `sending / accepted / applied / failed / timeout`
- observer 状态变化到来后 UI 可正确收敛
- 不扩张成完整控制台或多面板运维界面

### 执行块 5：联调说明与回归验证

**目标**：把控制主路径与失败路径收敛为可重复验证的 runbook。

**建议文件**：
- `docs/plans/2026-03-16-observer-demo-runbook.md` 或新增 v0.3 runbook
- 新增或更新测试文件
- 如需要，更新 `README.md`

**完成标准**：
- 说明 operator 配置、pairing、最小动作验证方法
- 说明 accepted / applied / timeout / failed 的检查步骤
- 说明既有 realtime observer 主路径回归检查步骤

## 7. 测试与验证策略

本阶段至少覆盖以下层次：

1. **operator / pairing 验证**：最小握手、成功与失败路径是否按约定工作
2. **控制请求契约验证**：请求入口、回执结构、错误语义是否稳定
3. **状态流转验证**：`sending` / `accepted` / `applied` / `failed` / `timeout` 是否按约定生效
4. **observer 关联验证**：控制后的最终状态是否由 observer realtime 流确认
5. **前端状态收敛验证**：UI 是否正确区分请求状态与实际生效状态
6. **回归验证**：既有 v0.2 列表页 / 详情页 realtime 主路径是否未被破坏

若当前自动化能力不足，应优先覆盖 operator / pairing、控制请求契约与请求状态流转，而不是先扩张复杂 UI 或多动作集。

---

## 8. 明确不推进的实现项

以下内容即便技术上可做，也不应在 v0.3 控制接入阶段提前推进：

- 完整控制动作全集
- `start` 的正式纳入（除非文档先更新并重新冻结）
- 完整 Agent 管理 UI（bindings / 全量管理）
- 多实例控制与跨实例消息路由
- 多用户登录、实例授权与共享权限模型
- 长期操作审计仓库
- 复杂补偿重试系统
- 完整聊天控制台或运维控制台

---

## 9. 进入实现前的提醒

在真正开始编码前，执行代理需要先确认：

- 当前 OpenClaw client 哪一层最适合承接 observer / operator 角色分流
- pairing 相关参数与失败语义应放在 client 层、service 层还是 API schema 层表达
- 控制请求与 observer realtime 事件之间，当前代码组织中最小可行的关联方式是什么
- 前端最小控制入口放在 `AgentDetail` 内联还是抽为独立组件更符合现有结构
- 哪些测试应先写 failing cases，再写最小实现

若在实现中发现需要突破单实例边界、引入多用户模型、破坏 v0.2 realtime 基线或新增复杂基础设施，应立即暂停并回到文档层处理，不得直接编码扩张。
