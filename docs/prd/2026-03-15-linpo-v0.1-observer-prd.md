# 灵盘（Linpo）v0.1 Observer PRD

> **状态**：当前有效产品需求文档
> 
> **来源**：基于 `docs/plans/2026-03-15-linpo-v0.1-observer-design.md` 的已确认设计共识整理。

## 1. 文档目的

本文档用于冻结 Linpo v0.1 的产品需求边界，明确它是什么、服务谁、验证什么，以及当前版本明确不做什么。

本文档是当前阶段的产品事实来源；后续架构文档与实施计划必须以本文档为约束。

---

## 2. 产品定义

Linpo v0.1 是一个**面向人类的 agent 运行观测入口**。

用户登录后，可以：

- 查看自己拥有的 agents
- 进入某个 agent 的详情页
- 通过拓扑视图观察该 agent 与其 subagents 的结构关系
- 通过最小状态与事件信息理解它们当前是否活跃、最近何时活跃、经历过哪些历史事件

Linpo v0.1 的目标不是替代 agent runtime，也不是成为新的编排平台，而是先提供一个比聊天框更适合“看懂 agent 系统”的交互入口。

---

## 3. 版本定位

### 3.1 v0.0：方向验证阶段

当前仓库此前承载的辩论 demo，应视为 Linpo 的 `v0.0`：

- 用于验证多 agent 参与、过程外显、主持人视角等交互语法
- 不再作为长期产品形态定义
- 不应继续主导当前产品边界

### 3.2 v0.1：Observer 产品起点

Linpo 的真正 v0.1 从“单 agent（含 subagents）运行观测”开始。

这一版本只回答一个核心问题：

> 人类能否通过结构化界面，而不是聊天流，更容易理解一个 agent / subagent 系统？

如果这个问题成立，Linpo 才有资格继续向后扩展。

---

## 4. 产品定位与价值

Linpo v0.1 的定位不是“更强的聊天框”，而是一个新的管理入口。

它要解决的核心问题是：

- 聊天框是线性的，不适合表达层级结构
- 当 agent 派生 subagents 后，人类难以持续维持全局认知
- 对话输出适合消费结果，不适合理解系统结构
- 管理者需要额外脑力，把线性叙事重新还原成运行关系

Linpo v0.1 的产品价值在于：

- 把隐藏在聊天流中的运行结构直接外显
- 让人类先“看清楚” agent 系统
- 为后续更强的任务、决策、控制能力提供稳定入口

---

## 5. 目标用户与用户行为

### 5.1 当前阶段的用户站位

v0.1 先不限定单一垂域，也不把自己锁定为开发者工具。

当前站位是：

- 先做通用入口
- 先抽象出 agent 运行观测这一通用能力
- 后续再决定是否向特定垂域演进

### 5.2 核心用户行为

v0.1 的核心用户行为非常明确：

1. 用户登录系统
2. 查看自己拥有的 agents
3. 进入某个 agent
4. 看清该 agent 与 subagents 的结构
5. 理解哪些节点当前活跃、最近何时活跃、发生过哪些事件

因此，v0.1 的第一目标不是“操作 agent”，而是“看懂 agent”。

---

## 6. 核心页面与主对象

### 6.1 主对象

v0.1 的主对象是 **Agent**。

当前不把 task、run、session 或 workspace 作为首页主对象。它们未来可以演进为次级视图，但不是当前产品入口。

### 6.2 页面结构

当前有效页面结构已冻结为四层入口：

- **`/overview`**：`agents-first watchlist`，作为默认 landing，先回答谁在干活、谁异常、谁值得巡视
- **`/topology`**：`graph-only` canvas + auto layout，只承接关系图主舞台与极简画布控件，不回退为配置工作台
- **`/kanban`**：`Mission Control` 风格只读板，聚合协作状态与关键工作信号，但不引入拖拽写回或审批
- **`/session/:instanceId/:agentId`**：极简 title / stream / input drill-down，桌面内容宽度上限固定为 `880px`

---

## 7. 成功标准

Linpo v0.1 的首要成功标准不是自动化、控制能力或运维深度，而是：

> 用户第一次进入后，能比聊天框更容易看懂一个 agent / subagent 系统的结构。

对应的验证问题包括：

- 用户是否能一眼分辨根 agent 与 subagents 的关系
- 用户是否能知道系统当前是否仍在运行
- 用户是否能知道某个节点最近是否活跃过
- 用户是否能通过历史事件理解节点经历过什么

---

## 8. 当前版本明确不做

为避免 v0.1 失焦，当前版本明确不做以下能力：

- 多 agent 编排
- 统一 runtime 控制
- 暂停 / 恢复 / 重试等控制操作
- 复杂任务系统
- 决策点追溯视图
- 资源监控视图
- 全局异常中心
- 用户 DIY 垂域视图
- 接入协议冻结

这些能力可以成为未来版本方向，但都不是 v0.1 的前置条件。

---

## 9. 演进边界

只有当 v0.1 证明"结构可见性"成立后，Linpo 才应继续向后扩展。

未来可能演进的方向包括：

- 任务进度视图
- kanban 视图
- 关键决策点追溯视图
- 资源监控视图
- 异常上浮与告警
- 轻量控制能力
- 用户自定义垂域视图
- 更强的多 agent 团队管理视图

但这些都不应反向影响当前 v0.1 的范围定义。

---

## 10. 版本演进规划

> **状态**：当前有效的版本路线图
>
> **前提**：Linpo 作为 OpenClaw 的补充入口，核心差异化是**多实例聚合观察 + 跨实例协作扩展能力**。
>
> **当前阶段判断**：v0.5 用户模型与实例配置已完成，当前应把产品收敛到 v0.6 的多实例聚合视图与 IA 语义，而不是继续保留 pre-v0.6 的旧 plans 作为活跃入口。

### 10.1 与 OpenClaw 的关系

| 维度 | 说明 |
|------|------|
| **底层协议** | 复用 OpenClaw Gateway WebSocket 协议，通过适配器层支持扩展 |
| **角色定位** | 补充入口，差异化在**多实例聚合 + 跨实例协作**，而非重新发明协议 |
| **多用户模型** | OpenClaw 是单用户多 agent；多用户隔离需在 Linpo 层实现 |
| **实例模型** | Linpo 聚合多个独立实例，每个用户配置自己的私有实例 |

### 10.2 版本路线图

```
v0.1 ─ Observer 起点（已完成）
v0.2 ─ Realtime Observer（已完成）
v0.3 ─ 单实例控制接入验证（已完成）
v0.4 ─ 单实例控制完善（已完成）
v0.5 ─ 用户模型 + 实例配置基础（已完成）
v0.6A ─ 多实例聚合数据与筛选闭环（已完成）
v0.6B ─ overview / topology / kanban / session IA 收敛 ← 当前目标
v0.7 ─ 跨实例消息传递
v0.8 ─ 文件系统视图 + 文件传递
v0.9 ─ 安全加固 + 审计
v1.0 ─ 内测 + 修复
v1.1 ─ 公开发布
```

### 10.3 v0.6 当前冻结边界

v0.6 当前冻结为以下产品结构：

| 层级 | 路由 | 职责 | 产品语义 |
|------|------|------|----------|
| **总览层** | `/overview` | 默认 landing | 全局脉搏主舞台，展示用户全部 agents，回答“谁在干活、哪里值得巡视” |
| **拓扑层** | `/topology` | `graph-only` 关系画布 | 实例 / agents / skills / 外接 ACP 的关系图主舞台，采用 auto layout，只保留极简画布控件 |
| **看板层** | `/kanban` | `Mission Control` 风格只读板 | 工作项、协作状态、关键工作信号 |
| **接管层** | `/session/:instanceId/:agentId` | drill-down | 单 agent 上下文承接页，作为 overview / topology / kanban 的统一进入目标，显式 URL 真源 |

### 10.4 v0.6 当前硬约束

- `/overview` 是默认 landing
- `/overview` 以用户全部 agents 为概览对象，承担概览 / 巡视入口
- `session/:instanceId/:agentId` 以 URL 参数为唯一真源
- `/session` 与 `/session/:instanceId` 仅作为兼容重定向入口
- `overview`、`topology` 与 `kanban` 三页都必须提供进入 agent 对话的入口，并统一落到 `/session/:instanceId/:agentId`
- 聚合读模型与前端展示必须统一使用 `request_id`、`freshness`、`partial_failure` / `diagnostics` 语义；错误包络至少包含 `code`、`message`、`request_id`、`recoverable`、`next_step`
- `freshness` 至少表达状态与时间戳，状态词汇冻结为 `fresh` / `stale` / `failed`
- 未授权、失败、部分成功场景都不得缺失 `request_id`，也不得把降级态伪装成 empty-success 或实时成功
- 首页汇报感禁止额外 prompt 注入，不允许通过静默向 agent 发送 prompt 来制造汇报内容
- topology 首期动作环只允许 `查看 / 进入 / 配置 / 关系`
- `topology` 主舞台固定为 `graph-only` canvas + auto layout，只允许极简画布控件；不承接详情侧栏、配置面板、统计卡或任何写操作
- 不在首期动作环或会话主路径暴露 pause/reset/send/delete 等 destructive/runtime controls
- `kanban` 作为 `Mission Control` 风格只读板存在，不引入拖拽写回、审批流或其他项目管理平台化能力
- 会话消息历史支持 Markdown 渲染
- 工具调用显示为摘要说明气泡，不直接展示原始 JSON
- 不引入模板系统、工作流平台化或控制面扩张
- 每个 major feature 完成后都必须部署，并在 ravin 上执行 Playwright 集成验证，覆盖改动功能与强相关链路
- 后端新增/修改的核心逻辑必须有完整单元测试覆盖
- 全部计划完成后，必须逐条核对实现成果是否符合 plan / PRD / architecture；若仍有偏差，继续补齐并重新核对

### 10.5 关键设计决策

| 决策 | 说明 |
|------|------|
| **v0.6 分阶段推进** | v0.6A 先做聚合数据、健康状态与筛选闭环，v0.6B 再做 IA 收敛 |
| **overview 默认 landing** | 默认入口必须统一到 `/overview` |
| **topology 固定为 graph-only 关系画布** | topology 只承担关系图主舞台与固定动作环，不再作为默认 landing，也不承接配置工作台语义 |
| **kanban 进入主导航** | kanban 承担聚合工作项与协作信号，但不成为通用管理平台 |
| **session drill-down 真源** | session 只以 `instanceId + agentId` 为事实来源 |
| **三页统一进入 agent 对话** | overview / topology / kanban 都必须显式跳转到 `/session/:instanceId/:agentId` |
| **消息历史样式收敛** | Markdown + tool-call 摘要气泡，禁止 raw JSON 暴露 |
| **分阶段验收** | 每个 major feature 后都部署并做 ravin Playwright 集成验证 |
| **范围排除项冻结** | 不引入模板系统、工作流平台化或控制面扩张 |
| **最终逐条回查** | 任务完成后必须逐条对照实现 / plan / PRD / architecture 再收口 |

### 10.6 v0.6B 四页 UI 角色冻结

- **overview**：主舞台 = `agents-first watchlist`，只回答谁在运行、谁异常、谁值得立刻巡视；次要区域 = 极小 summary 辅助区，只补充总数、异常数与筛选状态；禁止项 = 把 summary 做成大卡片首页、报告页、独立控制台或任何突破 `observer-only` 边界的写操作。
- **topology**：主舞台 = `graph-only` canvas，节点与边关系通过 auto layout 稳定呈现；次要区域 = 极简画布控件，如缩放、适配、图例提示；禁止项 = 详情侧栏、右侧 `配置面板`、统计卡、节点列表挤占主体、拖拽写回、画布外编辑器与其他写操作。
- **kanban**：主舞台 = `Mission Control` 风格只读板；次要区域 = 轻量筛选、统计与 freshness 提示；禁止项 = 拖拽写回、列内编辑、批量改状态、审批流、项目管理平台化，继续保持 `observer-only`。
- **session**：主舞台 = 极简标题 + 消息流 + 输入区，canonical 路径保持 `/session/:instanceId/:agentId`；次要区域 = 仅保留必要的 agent 身份与 freshness 辅助信息；禁止项 = `tabs`、`sidebar`、`status panel`、多栏工作台，桌面内容宽度上限固定为 `880px`。

### 10.7 能力依赖表

| 能力 | OpenClaw 支持 | Linpo 需实现 |
|------|-------------|-------------|
| 单实例观测 | ✅ WebSocket + snapshot | 前端视图 |
| 单实例 realtime 观测 | ✅ 最小 realtime 事件 | realtime 状态收敛、buffer、resync |
| 单实例控制协议接入 | ✅ operator scopes + device identity | role/scopes/pairing 接入 |
| 单实例最小控制闭环 | ✅ 基础控制请求 | 控制 UI、请求状态、观测反馈闭环 |
| 单实例 Agent 管理 | ✅ agents.list + bindings | 管理界面 |
| 文件系统访问 | ⚠️ 工具级（read/write/exec） | 文件浏览器封装 |
| **多实例聚合** | ❌ 不支持 | **Linpo 核心能力** |
| **跨实例消息路由** | ❌ 不支持 | **Linpo 核心能力** |
| **适配器抽象层** | N/A | **Linpo 需实现** |
| 多用户隔离 | ❌ 不支持 | Linpo 层实现 |
