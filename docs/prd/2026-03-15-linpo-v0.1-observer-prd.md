# 灵盘（Linpo）v0.1 IA PRD

> **状态**：当前有效产品需求文档
> 
> **来源**：基于当前已冻结的 README、architecture 与当前唯一 active plan 持续收敛。

## 1. 文档目的

本文档用于冻结 Linpo v0.1 的产品需求边界，明确它是什么、服务谁、验证什么，以及当前版本明确不做什么。

本文档是当前阶段的产品事实来源；后续架构文档与实施计划必须以本文档为约束。

---

## 2. 产品定义

Linpo v0.1 是一个**面向人类的多实例 agent 工作与协作入口**。

用户登录后，可以：

- 进入 `overview` 主页查看总体 token 消耗、agent 状态与全局事件
- 进入 `topology` 理解实例 / 智能体 / 会话 / 工具之间的 routing 关系
- 进入 `kanban` 以任务板方式查看与推进任务上下文
- 进入 `team` 以 persistent agent cards 方式进入团队与 agent 主入口
- 进入 `session` 作为会话工作区，在渠道与会话切换中继续对话

Linpo v0.1 的目标不是停留在只读 observer，也不是直接扩成任意平台化控制面，而是先建立一个与 `../` 参考仓库对齐、支持多实例的 5 页 IA 工作入口。

---

## 3. 版本定位

### 3.1 v0.0：方向验证阶段

当前仓库此前承载的辩论 demo，应视为 Linpo 的 `v0.0`：

- 用于验证多 agent 参与、过程外显、主持人视角等交互语法
- 不再作为长期产品形态定义
- 不应继续主导当前产品边界

### 3.2 v0.1：IA 产品起点

Linpo 的真正 v0.1 从新 5 页 IA 工作入口开始。

这一版本回答的核心问题是：

> 人类能否通过结构化 5 页 IA，而不是聊天流或旧 observer 入口，更容易理解并进入多实例 agent 工作系统？

如果这个问题成立，Linpo 才有资格继续向后扩展。

---

## 4. 产品定位与价值

Linpo v0.1 的定位不是“更强的聊天框”，而是一个新的管理入口。

它要解决的核心问题是：

- 聊天框是线性的，不适合表达层级结构
- 当 agent 派生 subagents 后，人类难以持续维持全局认知
- 对话输出适合消费结果，不适合理解系统结构
- 管理者需要额外脑力，把线性叙事重新还原成运行关系

Linpo v0.1 的产品价值在于：

- 把隐藏在聊天流中的运行结构直接外显
- 让人类先“看清楚” agent 系统
- 为后续更强的任务、决策、控制能力提供稳定入口

---

## 5. 目标用户与用户行为

### 5.1 当前阶段的用户站位

v0.1 先不限定单一垂域，也不把自己锁定为开发者工具。

当前站位是：

- 先做通用入口
- 先抽象出 agent 运行观测这一通用能力
- 后续再决定是否向特定垂域演进

### 5.2 核心用户行为

当前阶段的核心用户行为已经切换为：

1. 用户登录系统
2. 进入 `overview` 主页查看总体运行态势
3. 按需切换到 `topology / kanban / team`
4. 从 `team` 或其他具备明确上下文的入口进入某个 agent 的 `session` 工作区
5. 在 `session` 中切换渠道 / 会话并继续对话或承接当前上下文

因此，当前阶段的第一目标不是“只看懂 agent”，而是：

> 让用户在新 5 页 IA 中同时完成总体态势理解、结构理解、任务理解、团队入口与会话工作区承接。

---

## 6. 核心页面与主对象

### 6.1 当前主对象

当前阶段不再把单一 agent 作为唯一首页主对象，而是采用 **多实例 + 多页面分工** 的对象体系：

- `overview` 的主对象：总体 token / agent 状态 / 全局事件
- `topology` 的主对象：实例 / 智能体 / 会话 / 工具 的 routing 关系
- `kanban` 的主对象：任务
- `team` 的主对象：persistent agent cards
- `session` 的主对象：agent 工作区中的 channel + session 上下文

### 6.2 当前页面结构

当前有效页面结构已冻结为 **5 页 IA**：

- **`/overview`**：主页 / 默认入口；顶部为 token 统计与 agent 状态统计，主舞台为按实例分组的近期 token 消耗曲线，右侧为全局事件列表
- **`/topology`**：满屏 routing graph 画布；泳道固定为实例 / 智能体 / 会话 / 工具，结构语言对齐 `openclaw/geteway-routing-graph`
- **`/kanban`**：任务板；每卡一个任务，交互和板面能力对齐 `openclaw/mission-control`
- **`/team`**：团队页；persistent agent cards 主舞台，对齐 `openclaw/center` 的 `Staff` 页面
- **`/session/:agentId/:channelKey/:sessionKey`**：会话工作区 canonical 路由；从 agent 进入，侧栏固定为“渠道在上，会话在下”，主区域为当前会话

### 6.3 当前硬约束

- `/overview` 是默认 landing
- `session` 不再是旧的极简 drill-down，而是可开放对话的工作区
- `/session/:agentId/:channelKey/:sessionKey` 是当前 canonical session 路由
- 空工作区 canonical 路由固定为 `/session/:agentId/__none__/__new__`
- 空会话 canonical 路由固定为 `/session/:agentId/:channelKey/__new__`
- `__none__` 与 `__new__` 为保留字；若外部系统存在同名 key，进入当前系统前必须按稳定转义规则处理
- `team` 为当前有效第三页，不是附录或 future work
- overview / topology / kanban / team / session 五页都必须显式承接 `request_id`、`freshness`、`partial_failure` / `diagnostics` 等真实读链路线索
- 当前有效页面集合只包括这 5 页；`settings / profile` 暂时搁置

---

## 7. 成功标准

Linpo v0.1 的首要成功标准不是自动化、控制能力或运维深度，而是：

> 用户第一次进入后，能比聊天框更容易看懂一个 agent / subagent 系统的结构。

对应的验证问题包括：

- 用户是否能一眼分辨根 agent 与 subagents 的关系
- 用户是否能知道系统当前是否仍在运行
- 用户是否能知道某个节点最近是否活跃过
- 用户是否能通过历史事件理解节点经历过什么

---

## 8. 当前版本明确不做

为避免当前阶段失焦，当前版本明确不做以下能力：

- `settings` 页面
- `profile` 页面
- 未冻结的第六个有效主页面
- 与当前 5 页 IA 无关的额外平台化扩张
- 以 README / PRD / architecture 之外的口头约定替代当前唯一 plan

这些能力可以成为后续版本方向，但都不是当前阶段的前置条件。

---

## 9. 演进边界

只有当 v0.1 证明"结构可见性"成立后，Linpo 才应继续向后扩展。

未来可能演进的方向包括：

- 任务进度视图
- kanban 视图
- 关键决策点追溯视图
- 资源监控视图
- 异常上浮与告警
- 轻量控制能力
- 用户自定义垂域视图
- 更强的多 agent 团队管理视图

但这些都不应反向影响当前 v0.1 的范围定义。

> **状态**：当前文档仅冻结当前有效范围。
>
> **当前阶段目标**：把 Linpo 的当前 active UI 基线整体切换为新 5 页 IA，并在当前仓库内完成对应实现与验收收口。
>
> **当前阶段约束**：当前 `/start-work` 只允许使用 `.sisyphus/plans/ui-design-realignment-work-plan.md` 这一份 active plan；`docs/plans/` 不参与当前执行。

### 10.1 与 OpenClaw 的关系

| 维度 | 说明 |
|------|------|
| **底层协议** | 复用 OpenClaw Gateway WebSocket 协议，通过适配器层支持扩展 |
| **角色定位** | 建立多实例工作与协作入口，差异化在**多实例聚合 + 任务板 + 团队入口 + 会话工作区**，而非重新发明协议 |
| **多用户模型** | OpenClaw 是单用户多 agent；多用户隔离需在 Linpo 层实现 |
| **实例模型** | Linpo 聚合多个独立实例，每个用户配置自己的私有实例 |

### 10.2 附录：长远规划

`v0.6` 之后的版本方向统一收纳在 `docs/plans/`，不在本文档中展开，也不参与当前阶段执行。

### 10.3 v0.6 当前冻结边界

v0.6 当前冻结为以下产品结构：

| 页面 | 路由 | 职责 | 产品语义 |
|------|------|------|----------|
| **Overview** | `/overview` | 默认 landing / 主页 | 顶部 token / agent 状态统计，主舞台为实例 token 曲线，右侧为全局事件列表 |
| **Topology** | `/topology` | routing graph 页面 | 满屏四泳道画布：实例 / 智能体 / 会话 / 工具 |
| **Kanban** | `/kanban` | 任务板 | 每卡一个任务，能力锚点为 `openclaw/mission-control` |
| **Team** | `/team` | 团队主入口 | persistent agent cards 主舞台，结构锚点为 `openclaw/center` 的 `Staff` 页面 |
| **Session** | `/session/:agentId/:channelKey/:sessionKey` | 会话工作区 | 从 agent 进入；渠道在上，会话在下，主区域为当前会话 |

### 10.4 v0.6 当前硬约束

- `/overview` 是默认 landing
- `overview` 不再是旧 watchlist 首页
- `topology` 不再按旧 graph-only observer 口径定义，而按 routing graph 画布定义
- `kanban` 不再按只读板定义，而按任务板定义
- `team` 是当前有效第三页，不得遗漏或降级为附录
- `session` 不是旧极简 drill-down；允许真实对话能力
- `session` 当前唯一 canonical 路由为 `/session/:agentId/:channelKey/:sessionKey`
- 空工作区 canonical 路由固定为 `/session/:agentId/__none__/__new__`
- 空会话 canonical 路由固定为 `/session/:agentId/:channelKey/__new__`
- overview / topology / kanban / team / session 五页都必须承接真实读链路线索：`request_id`、`freshness`、`partial_failure` / `diagnostics`
- 首页汇报感禁止额外 prompt 注入，不允许通过静默向 agent 发送 prompt 来制造汇报内容
- 会话消息历史支持 Markdown 渲染
- 工具调用显示为摘要说明气泡，不直接展示原始 JSON
- 当前阶段不引入 `settings / profile` 或额外第六个有效主页面
- 每个 major feature 完成后都必须部署，并在 ravin 上执行 Playwright 集成验证，覆盖改动功能与强相关链路
- 后端新增/修改的核心逻辑必须有完整单元测试覆盖
- 全部计划完成后，必须逐条核对实现成果是否符合 plan / PRD / architecture；若仍有偏差，继续补齐并重新核对

### 10.5 当前阶段关键决策

| 决策 | 说明 |
|------|------|
| **v0.6 分阶段推进** | `v0.6A` 已形成当前稳定基线；当前继续推进新 5 页 IA 的 truth-doc 对齐、实现与验收收口 |
| **overview 默认 landing** | 默认入口必须统一到 `/overview` |
| **topology 固定为 routing graph 画布** | topology 只承担四泳道 routing graph 主舞台，不再使用旧 `graph-only observer` 定义 |
| **kanban 进入主导航并按任务板定义** | kanban 承担任务板主舞台，不再以只读信号板定义当前页面 |
| **team 进入主导航** | team 承担 persistent agent cards 主舞台，是当前有效第三页，不得缺位 |
| **session canonical 真源切换** | session 当前 canonical 路由为 `/session/:agentId/:channelKey/:sessionKey`，并配套空工作区与空会话 canonical 变体 |
| **消息历史样式收敛** | Markdown + tool-call 摘要气泡，禁止 raw JSON 暴露 |
| **分阶段验收** | 每个 major feature 后都部署并做 ravin Playwright 集成验证 |
| **范围排除项冻结** | 不引入 `settings / profile` 与未冻结的第六个有效页面 |
| **最终逐条回查** | 任务完成后必须逐条对照实现 / plan / PRD / architecture 再收口 |

### 10.6 当前五页 UI 角色冻结

- **overview**：主舞台 = 顶部 token 统计 + agent 状态统计 + 按实例分组的近期 token 曲线 + 右侧全局事件列表；禁止项 = 回退成 `agents-first watchlist`、大摘要首页或旧 observer 首页。
- **topology**：主舞台 = 四泳道满屏 routing graph 画布；禁止项 = 回退成旧 `graph-only` observer 画布、详情侧栏/配置面板挤占主舞台、旧 skill/ACP 一等泳道语义。
- **kanban**：主舞台 = 任务板；禁止项 = 按“Mission Control 风格只读板”继续定义当前页面、以 agent 卡片取代 task card、把 kanban 缩回 overview 衍生页。
- **team**：主舞台 = persistent agent cards；禁止项 = 缺位、附录化、可选化，或退回为普通 agent 列表子组件。
- **session**：主舞台 = agent header + 渠道区 + 会话区 + 当前会话区 + 输入/发送区；canonical 路径 = `/session/:agentId/:channelKey/:sessionKey`；禁止项 = 回退为旧 `/session/:instanceId/:agentId` 真源、极简 drill-down 单列页、只读会话页。

### 10.7 能力依赖表

| 能力 | OpenClaw 支持 | Linpo 需实现 |
|------|-------------|-------------|
| 单实例观测 | ✅ WebSocket + snapshot | 前端视图 |
| 单实例 realtime 观测 | ✅ 最小 realtime 事件 | realtime 状态收敛、buffer、resync |
| 单实例控制协议接入 | ✅ operator scopes + device identity | role/scopes/pairing 接入 |
| 单实例最小控制闭环 | ✅ 基础控制请求 | 控制 UI、请求状态、观测反馈闭环 |
| 单实例 Agent 管理 | ✅ agents.list + bindings | 管理界面 |
| 文件系统访问 | ⚠️ 工具级（read/write/exec） | 文件浏览器封装 |
| **多实例聚合** | ❌ 不支持 | **Linpo 核心能力** |
| **跨实例消息路由** | ❌ 不支持 | **Linpo 核心能力** |
| **适配器抽象层** | N/A | **Linpo 需实现** |
| 多用户隔离 | ❌ 不支持 | Linpo 层实现 |
