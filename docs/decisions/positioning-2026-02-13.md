# 产品定位决策记录 (2026-02-13)

> ⚠️ 已过时：本文档为历史决策记录，当前产品方向与需求范围以 `docs/prd/2026-02-26-lingban-prd-v3.0.md` 为准。

本文档用于记录本项目的产品定位与 P0 方向决策要点（面向人类/产品/研发/运维），避免在实现过程中反复摇摆。

## 背景

我们需要先把业务定位做好：做的是“把构建权从开发者转移给业务专家”的生意。

我们的用户从来不是开发者，而是那个懂业务、懂用户、对结果负责，但被代码与排期困住的人。

该产品不是一个工具，而是一个“应用分娩师”（Application Midwife）：把业务意图分娩成可运行、可监控、可干预、可迭代的长期服务。

## 决策要点

1. 定位与用户
   - 目标用户：业务专家（非开发者）。
   - 定位：应用分娩师（把构建权从开发者转移给业务专家）。

2. 产品主线
   - 我们做的是“构造简单的长期服务”，而不是一次性自动构建产品。
   - “看班模式”不是视觉方案，是数据方案：用户一扫眼的安心来自实时、精准、可信的任务状态数据。
   - 支持“多线程非关联任务监控 + 调度”：同一用户需要同时盯 3-5 条线。

3. P0 必须自研 (立即启动)
   - 任务状态管理规范与暴露协议（前端生命线）。
   - 用户干预接口（暂停/重试/转派等，交互差异点）。

4. 允许停下来确认
   - 允许系统在不确定时停下来向用户确认（open questions / human-in-the-loop），不强行一次性输出完整图谱。

5. 取舍
   - 放弃 Vercel 动态部署独立子域（暂不做）。优先复用现有能力与现有部署方式。
   - 不做泛内容生成（那是另一类产品），不做纯 BI（那是另一类产品）。

## 影响与后果

- 后端优先级前置：必须先长出状态中心与干预动作模型，前端才能“一眼有价值”。
- 任何编排/模拟/智能体输出，最终都要落到可投影、可回放、可排序的状态事件上，否则无法建立信任。
- “允许停下来确认”要求状态机必须显式表达 `blocked_user/needs_human`，并在前端给出可执行的下一步动作。

## 后续工作

P0 开发顺序建议：

1. 定义并实现状态协议（事件类型、状态枚举、排序/去重规则、snapshot 结构、WS 推送）
2. 定义并实现干预接口（pause/retry/reassign/cancel），并保证事件流可审计可回放
3. 在“看班模式”UI 上验证：同时盯 3-5 条非关联任务时，用户能快速定位卡点并执行干预
